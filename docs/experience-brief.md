# 技術釣り LP — Experience Brief

## 目的

技術釣りを初めて見る人に、「技術の違いを、魚の動きや引きとして体験するゲーム」だと短時間で伝え、実際に遊ぶ入口へつなぐ。LPのスクロールそのものを、小さな海中探索として楽しめるようにする。

## 中心となる演出

画面上から竿先と一本の糸が垂れ、訪問者はその糸を視線で追いながら海へ潜る。スクロールは深度の進行を担当し、風と潮は控えめな横方向の動きを担当する。水面では風紋、水中では浮遊物や泡の流れを使い、背景全体を大きく揺らさない。

魚は突然表示しない。水の反応や餌へ寄る気配、薄い影、輪郭、魚体の順に段階的に現し、スクロールを戻せば自然に逆の状態へ戻る。

## 仮のストーリーボード

1. **海面 / Hero** — 明るい水、垂れる竿先と糸。魚はまだ見せない。作品を一文で説明し、すぐ押せるゲーム開始CTAを置く。
2. **水面下** — 水面の反射が弱まり、糸が水へ入る。PCとスマホで釣る遊びを短く説明する。
3. **浅い層 / Go魚** — 一匹から群れへ分かれ、複数方向へ動く。並行処理の比喩として紹介する。
4. **中層 / Dockerクジラ** — 重い慣性のある動きと糸への負荷を見せる。コンテナと実行環境の比喩として紹介する。
5. **暗い層 / CSS fish** — 魚の形は保ちながら、状態に応じて色や模様が変わる。構造と見た目の分離の比喩として紹介する。
6. **浮上・CTA** — 魚を釣り上げる短いクライマックスの後、ゲームへの明快な導線へ戻す。

深さは物語上の演出であり、「深い魚ほど高等な技術」という序列を意味しない。K8sレヴィアタンは実験的な魚種として、初期LPでは既定で扱わない。

## UXの必須条件

- 最初の画面だけで、作品の内容と遊び始める方法が分かる。
- CTAはスクロールを完了しなくても使える。探索演出を遊ぶことをゲーム開始の条件にしない。
- ネイティブスクロールを維持し、強制スナップやスクロールの乗っ取りをしない。
- 暗い場面でも本文とCTAの可読性を保つ。意味のある説明をアニメーションだけに閉じ込めない。
- `prefers-reduced-motion`では大きな移動・視差を止め、静止表示でも情報が欠けないようにする。
- モバイル、特にiPhone Safariで、糸の連続性、戻りスクロール、タップしやすいCTAを確認する。

## 技術方針（仮）

- **Astro + TypeScriptの静的出力**を第一候補とする。LP本文と見出しは静的HTML、スクロール演出の制御は小さなTypeScript、3Dは必要性を検証してから追加する。
- Three.jsを採用する場合も、LP全体を常時レンダリングせず、単一の水中シーンに限定する。遅延読込、画面外での停止、モバイル向け描画負荷の上限、WebGLなしの代替表示を用意する。
- DB、認証、ゲーム状態、WebSocketは作らない。LPの仕事は紹介とゲームへの案内まで。
- 現行ゲームのコードや素材を無条件でコピーしない。ロゴ・魚モデル・画像を再利用する場合は、所有・利用条件と更新方法を確認して必要なものだけ持ち込む。
- ゲームへの遷移先URLは、実際に公開されている正しいURLを確認してから設定する。仮URLを本番リンクとして公開しない。

## 初期スコープ

含める: 1ページの縦スクロール体験、作品説明、魚と技術の対応、ゲーム開始CTA、モーション軽減・3D非対応時の代替。

含めない: ゲーム本体の変更、ゲームプレイの埋め込み、サーバー/API/DB、ログインやユーザー別データ、デプロイと公開。

## 未決事項

- ハッカソン後に使う正式なゲームURLとLPの公開先
- LPで使うタイトル・コピー・言語（日本語のみかどうか）
- 既存ロゴや魚モデルを使うか、LP専用に描き直すか
- 3Dを初版から入れるか、SVG/CSSプロトタイプで体験を先に確かめるか
- ページ長、魚の出現順、各場面の文章量

## 制作順

1. ハッカソン後にこのブリーフと既存ゲームの最新状態を見直す。
2. 静止画・HTML・CSS/SVGだけで、HeroからCTAまでの短い流れを組む。
3. モバイルで体験が伝わることを確認してから、必要なら一つのThree.jsシーンを追加する。
4. iPhone Safari、デスクトップ、動きを減らす設定、WebGL非対応、低負荷端末で検証する。
5. ゲームURLと公開先を確認し、ユーザーの依頼があればデプロイする。
